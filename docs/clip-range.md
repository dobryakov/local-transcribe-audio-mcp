# Обрезка аудио по диапазону start–end

> Статус: design · не реализовано · 2026-10-29  
> Связано с: [design.md](design.md) §5.1 (convert), §6 (параметры задачи)

## 1. Цель

Позволить указать участок загруженного файла (`start`–`end`), чтобы дальше по пайплайну (диаризация → ASR → Markdown) шла **только эта часть**. Типичный кейс: двухчасовая запись Zoom, нужна расшифровка только середины встречи.

Файл по-прежнему загружается целиком (одноразовая ссылка / REST). Обрезка — серверный шаг на этапе convert, до диаризации и ASR.

## 2. Решение (зафиксировано)

| Тема | Решение |
|---|---|
| Параметры | `start_s` и `end_s` (секунды, float), оба **опциональны** |
| Где резать | Этап `convert`: тот же `ffmpeg`, что уже нормализует в 16 kHz mono WAV |
| Таймкоды в Markdown | **Абсолютные** — как в исходном файле (`start_s` + локальное время клипа) |
| `duration_s` в статусе задачи | Длительность **клипа** (что реально обработали) |
| UI upload-страницы | Поля не добавляем в первой итерации: диапазон задаёт Claude/клиент при создании задачи |
| Миграция БД | Не нужна: `params` уже JSON |

## 3. Параметры API / MCP

Добавляются ко всем существующим точкам создания задачи (как `language`, `prompt`, …):

| Поле | Тип | Дефолт | Смысл |
|---|---|---|---|
| `start_s` | float ≥ 0 | `0` (начало файла) | Начало участка, секунды от начала файла |
| `end_s` | float > `start_s` | конец файла | Конец участка (не включая, как `-to` у ffmpeg) |

Точки входа:

- `POST /v1/jobs` — form-поля `start_s`, `end_s`
- `POST /v1/upload-links` — JSON-тело
- MCP `create_upload_link(..., start_s?, end_s?)`
- CLI `transcribe-upload` — флаги `--start` / `--end` (когда появится/обновится)

Пример MCP-сценария:

> «Расшифруй только с 45-й минуты до 1:10» → Claude вызывает  
> `create_upload_link(language="multi", num_speakers=2, start_s=2700, end_s=4200, …)`.

Форматы вроде `45:00` / `1:10:00` **не принимаем на сервере** — парсит клиент (Claude) в секунды. Так API остаётся простым и однозначным.

### Валидация (`JobParams.validate`)

1. Если задан только один параметр — ок (`start_s` без `end_s` = «с этой секунды до конца»; `end_s` без `start_s` = «с нуля до end»).
2. `start_s >= 0`, `end_s > 0`.
3. Если оба заданы: `end_s > start_s`.
4. Длина клипа `(end_s - start_s)` ≤ `MAX_DURATION_MIN` (сейчас 240 мин). Если `end_s` не задан — проверка длины клипа откладывается до upload (когда известна длительность файла).
5. Нечисловые / отрицательные значения → `400`.

### Валидация при upload (`_validate_audio`)

После `ffprobe` полной длительности файла `D`:

| Условие | Ответ |
|---|---|
| `start_s >= D` | `400` — старт за пределами файла |
| `end_s` задан и `end_s > D` | **clamp** до `D` (тихий, логируем); либо жёсткий `400` — см. §7, по умолчанию clamp |
| эффективная длина клипа > `MAX_DURATION_MIN` | `400` — «audio too long» |
| клип короче ~0.5 с | `400` — слишком короткий участок |

Лимит `MAX_UPLOAD_MB` по-прежнему на **весь** загруженный файл (обрезка не уменьшает upload).

## 4. Изменения в пайплайне

### 4.1 `JobParams` (`app/models.py`)

```python
start_s: Optional[float] = None
end_s: Optional[float] = None
```

Поля входят в `to_dict` / `from_dict` / `validate`.

### 4.2 `convert` (`worker/stages/convert.py`)

Сигнатура: `convert(original, work_dir, *, start_s=None, end_s=None) -> dict`.

Команда ffmpeg (точность важнее скорости — вход уже один раз, выход PCM):

```bash
ffmpeg -y -loglevel error -i original.ext \
  [-ss <start_s>] [-to <end_s>] \
  -vn -ac 1 -ar 16000 -c:a pcm_s16le audio.wav
```

- `-ss` / `-to` **после** `-i` — decode+seek, точнее на переменном битрейте и контейнерах без индекса.
- Если параметр не задан — флаг не передаём (текущее поведение).
- `probe_duration` после конверта даёт длительность клипа → `convert.json`:

```json
{
  "wav": ".../audio.wav",
  "duration_s": 1500.0,
  "clip_start_s": 2700.0,
  "clip_end_s": 4200.0
}
```

`clip_start_s` / `clip_end_s` — эффективные значения после clamp (то, что реально вырезано). Нужны для сдвига таймкодов и шапки Markdown. Если обрезки не было: `clip_start_s=0`, `clip_end_s=duration_s` файла (или поля можно опустить — тогда offset = 0).

Оригинал по-прежнему удаляется сразу после успешного convert ([design.md](design.md) §5.1).

### 4.3 Downstream (diarize / asr / merge)

Работают **как сейчас** по `audio.wav`. Их локальные таймкоды начинаются с 0 (относительно клипа). Менять модели и форматы `words.json` / `turns.json` не нужно.

### 4.4 Сдвиг таймкодов (абсолютные)

В `merge.run` или сразу после него, перед записью `transcript.json`:

```
word.start  += clip_start_s
word.end    += clip_start_s
# то же для utterances после сборки
```

Либо сдвиг только на этапе render — тогда канонический `transcript.json` остаётся относительно клипа, а Markdown показывает абсолют. **Предпочтение:** сдвигать в merge, чтобы канонический JSON совпадал с тем, что видит пользователь (и будущие SRT/VTT из бэклога).

`duration_s`, передаваемый в `mark_done` и шапку: **длина клипа**, не исходного файла. В шапке Markdown дополнительно строка при ненулевом клипе:

```markdown
- Участок исходного файла: 00:45:00–01:10:00
```

### 4.5 Resume

Если `audio.wav` + `convert.json` уже есть (рестарт воркера) — reuse как сейчас. В `convert.json` уже лежат `clip_*`; повторно читать `params` для сдвига не обязательно, если merge берёт offset из meta.

## 5. Поверхности, которые трогаем

| Файл / место | Что |
|---|---|
| `app/models.py` | поля + validate |
| `app/main.py` | form / JSON → JobParams; `_validate_audio` с учётом клипа |
| `app/mcp_server.py` | аргументы + docstring (`start_s`/`end_s` в секундах, пример «45 мин → 2700») |
| `worker/stages/convert.py` | ffmpeg `-ss`/`-to`, meta |
| `worker/pipeline.py` | проброс params в convert; offset в merge |
| `worker/stages/merge.py` (или pipeline) | `+= clip_start_s` |
| `worker/render/markdown.py` | строка «Участок…» |
| `docs/design.md` | одна строка в таблице параметров §6 + пункт в бэклоге/статусе после реализации |
| upload.html | **не трогаем** в v1 фичи (диапазон уже в job params) |

Схема SQLite не меняется.

## 6. Поведение наружу

| Ситуация | Результат |
|---|---|
| Параметры не заданы | Как сейчас — весь файл |
| `start_s=2700`, `end_s=4200` | WAV ≈ 25 мин; таймкоды `[00:45:03–…]` |
| Только `start_s=3600` | С 1:00:00 до конца; `duration_s` = D − 3600 |
| Только `end_s=600` | Первые 10 минут |
| Клип 25 мин из файла 3 ч | Upload 3-часового файла ок по `MAX_DURATION_MIN`, если длина **клипа** ≤ лимита |

Статус `GET /v1/jobs/{id}`: `duration_s` = клип. При желании позже можно добавить `source_duration_s` / `clip` в публичный статус — **не в первой итерации**.

## 7. Риски и краевые случаи

| Риск | Митигация |
|---|---|
| Неточный seek на m4a/mp3 | `-ss` после `-i`; выход всё равно PCM 16 kHz — ошибка обычно < 1 с, для диаризации приемлемо |
| `end_s` чуть больше D из-за округления клиента | Clamp до D + лог |
| Клиент путает мм:сс и секунды | Docstring MCP явно: «seconds from start of file»; пример 45 мин = 2700 |
| Resume со старым `convert.json` без `clip_*` | Offset = 0 (обратная совместимость) |
| Двойной сдвиг при повторном merge | Сдвиг один раз при сборке transcript из words; words на диске остаются локальными *или* сдвиг идемпотентно хранит флаг — проще: words/turns всегда локальные (0-based), сдвиг только в `transcript.json` |

Зафиксированный порядок таймингов на диске:

1. `words.json`, `turns.json` — относительно клипа (0 … duration_clip).
2. `transcript.json` / Markdown — абсолютные (относительно исходного файла).

## 8. Оценка объёма

~1–2 часа чистой работы: модель параметров, convert, валидация upload, offset в merge/render, MCP docstring. Тесты вручную: короткий mp3 с `start_s`/`end_s`, проверка шапки и первого таймкода; без параметров — регрессия «весь файл».

## 9. План реализации (когда делать)

1. `JobParams` + валидация.
2. `convert` + `convert.json` meta; проброс из `pipeline`.
3. Сдвиг в merge → абсолютные таймкоды; строка в Markdown.
4. REST form + upload-links + `_validate_audio`.
5. MCP args + docstring.
6. Ручной прогон; обновить таблицу параметров в [design.md](design.md) §6.

## 10. Вне скоупа

- Несколько диапазонов в одной задаче (склейка кусков).
- Обрезка уже готового транскрипта без повторного ASR.
- Поля start/end на странице `/u/{token}`.
- Приём строк `"1:10:00"` на сервере.
- `source_duration_s` в публичном статусе (можно добавить позже без ломки).
