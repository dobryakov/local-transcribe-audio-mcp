# Transcribator — личный сервис транскрибации с диаризацией

> Статус: проект (design doc), v1 · 2026-10-29
> Автор: Григорий Добряков

## 1. Цель

Личный сервис, который превращает аудиозаписи переговоров, собеседований и встреч (60–120 минут) в текст **с разделением на спикеров и таймингами**. Работает локально на текущем сервере, без платных API. Доступен:

- по **REST API** (curl, скрипты, n8n);
- по **MCP**, чтобы Claude (Claude Code на этом сервере, Claude Code на ноутбуке, Claude.ai / Desktop) мог сам запускать транскрибацию и читать результат.

Авторизация — по API-ключу.

### Зафиксированные требования

| Тема | Решение |
|---|---|
| Языки | Параметр `language`, по умолчанию `en`. Записи бывают **смешанные en+ru** → нужен режим `multi` с определением языка по сегментам |
| Модель ASR | Выбирается в запросе (`model`), есть разумный дефолт |
| Диаризация | Два бэкенда за одним интерфейсом: `pyannote` и `sherpa`, выбор параметром |
| Спикеры | Подсказка количества: `num_speakers` или `min_speakers` / `max_speakers`. Метки анонимные (`SPEAKER_1`, `SPEAKER_2`, …) |
| Формат результата | Markdown-диалог с таймингами |
| Загрузка аудио | HTTP upload в REST API; варианты для Claude.ai описаны в §7 |
| Хранение | Аудио удаляется сразу после обработки; транскрипты хранятся бессрочно (удаление вручную) |
| Нагрузка | Строго одна задача за раз, контейнер ограничен по CPU/RAM |
| Готовность | Polling статуса (прогресс + ETA) |
| MCP-клиенты | Claude Code здесь (localhost), Claude Code на ноутбуке, Claude.ai / Desktop (remote) |

### Не входит в v1

Узнавание людей по голосу, переименование спикеров на сервере (это делает Claude по контексту), SRT/VTT/JSON-выгрузки наружу, webhooks/Telegram, суммаризация. Всё это — кандидаты в §13.

## 2. Ограничения сервера

Снято на 2026-10-29:

| Ресурс | Значение | Что это значит |
|---|---|---|
| CPU | 4 vCPU Intel Xeon Skylake, **AVX-512** | CTranslate2 и ONNX Runtime хорошо используют AVX-512 + int8 |
| GPU | нет | Только CPU-инференс |
| RAM | 7.6 ГБ всего, **~3.5 ГБ доступно**, swap 8 ГБ (занято 4 ГБ) | Главное узкое место. Модели надо грузить по очереди и выгружать |
| Диск | 21 ГБ свободно | Хватит на модели (~5 ГБ) и временные WAV |
| Соседи | ~30 контейнеров: WordPress, nginx-сайты, n8n + worker, Postgres, Chroma, browserless, MCP-серверы | Транскрибация не должна их «положить» |
| Reverse proxy | **Caddy** (`n8n-docker-caddy-caddy-1`) на 80/443 с авто-TLS | Через него сервис и публикуем наружу |
| ОС / Docker | Ubuntu 24.04, Docker 28.4 | Деплой через docker compose |

**Вывод:** сервис работает **асинхронно** (запись на 2 часа обрабатывается десятки минут), в одном воркере, этапы идут последовательно, и в памяти одновременно держится только одна модель. Если планируется много `large-v3-turbo` или пара записей в день, то **апгрейд до 16 ГБ RAM даст больше, чем любая оптимизация кода**.

## 3. Выбор технологий

### 3.1 Распознавание речи (ASR): faster-whisper

[faster-whisper](https://github.com/SYSTRAN/faster-whisper) — Whisper на движке CTranslate2. На CPU в int8 работает в несколько раз быстрее оригинального Whisper и потребляет меньше памяти.

Почему именно он:
- лучший бесплатный вариант для **en+ru** в одной модели;
- `multilingual=True` определяет язык **на каждом сегменте**, это наш кейс смешанных записей;
- встроенный Silero VAD (`vad_filter=True`) вырезает тишину: обработка быстрее, меньше галлюцинаций;
- `word_timestamps=True` даёт тайминги на уровне слов, они нужны для склейки со спикерами.

Не берём: **WhisperX** (wav2vec2-выравнивание завязано на одну языковую модель, смешанные записи ломают его, плюс лишний PyTorch-вес), **whisper.cpp** (на CPU сравним по скорости, но Python-интеграция и word timestamps хуже), **GigaAM/Vosk** (хороши для ru, но не умеют en+ru в одной записи).

**Модели (параметр `model`):**

| `model` | RAM (int8, оценка) | Качество en / ru | Примечание |
|---|---|---|---|
| `small` | ~0.8 ГБ | норм / слабовато | Быстрый черновик |
| `medium` | ~1.8 ГБ | хорошо / норм | Запасной вариант |
| `large-v3-turbo` | ~1.8 ГБ | отлично / хорошо | **Дефолт.** Энкодер от large-v3, облегчённый декодер: на CPU по скорости ≈ medium, по качеству заметно лучше |

`large-v3` (полный) в v1 не включаем: на 4 vCPU и в 4 ГБ лимита он слишком медленный и рискует упасть по памяти. Дефолт подтверждаем бенчмарком на этапе 1 (§12).

Ключевые параметры инференса: `compute_type="int8"`, `cpu_threads=3`, `beam_size` (дефолт 5, для `small` — 1), `vad_filter=True`, `condition_on_previous_text=False` (меньше «зацикливаний» на длинных записях), `initial_prompt`/`hotwords` из параметра `prompt` (имена, термины, названия компаний).

### 3.2 Диаризация: два бэкенда

| | `pyannote` (дефолт) | `sherpa` |
|---|---|---|
| Пакет | `pyannote.audio` 4.x, пайплайн `pyannote/speaker-diarization-community-1` (запасной — `speaker-diarization-3.1`) | `sherpa-onnx`: сегментация `pyannote-segmentation-3.0` (ONNX) + эмбеддинги (WeSpeaker / 3D-Speaker / NeMo TitaNet, выбираем на бенчмарке) |
| Качество | Лучшее среди бесплатных, хорошо определяет число спикеров сам | Чуть хуже, особенно без `num_speakers` |
| Ресурсы | PyTorch CPU, ~1–1.5 ГБ RAM, медленнее | ONNX Runtime без PyTorch, ~0.3–0.5 ГБ, быстрее в разы |
| Лицензия / доступ | Модели gated: нужен бесплатный HF-токен и один раз принять условия. Нужен **только для скачивания**, дальше работа офлайн (`HF_HUB_OFFLINE=1`) | Полностью открыто, без регистрации |
| Когда выбирать | Важные переговоры, много спикеров, неизвестно сколько людей | Быстро, известно число спикеров (1-на-1 собеседование) |

Оба бэкенда реализуют один интерфейс:

```python
class Diarizer(Protocol):
    def diarize(self, wav_path: Path, num_speakers: int | None,
                min_speakers: int | None, max_speakers: int | None,
                progress: Callable[[float], None]) -> list[Turn]: ...
    # Turn = (start: float, end: float, speaker: str)
```

`diarization=none` пропускает этап (полезно для записей одного человека, например диктовки).

### 3.3 Остальной стек

| Компонент | Выбор | Почему |
|---|---|---|
| Язык | Python 3.12 | Вся ML-экосистема |
| HTTP | FastAPI + uvicorn | Стриминговый upload, OpenAPI из коробки |
| MCP | Официальный `mcp` Python SDK (FastMCP), транспорт **Streamable HTTP**, смонтирован в то же FastAPI-приложение на `/mcp` | Один процесс, одна авторизация, работает и локально, и через remote connector |
| Очередь и метаданные | **SQLite** (WAL), таблица `jobs` как очередь | Redis/Celery ради одной задачи за раз не нужны и съедят RAM |
| Аудио | `ffmpeg` / `ffprobe` | Любой входной формат (m4a, mp3, ogg, opus, wav, webm, mp4/mov — дорожка из видео) → WAV 16 кГц mono |
| Деплой | docker compose, 2 сервиса из одного образа | Изоляция и лимиты ресурсов |
| TLS / публикация | Существующий Caddy | Уже стоит, авто-TLS, нет лимита на размер тела |

```
             Claude Code (здесь)        Claude Code (ноут)        Claude.ai / Desktop
                    │ http://127.0.0.1         │ https                    │ https (remote connector)
                    ▼                          ▼                          ▼
             ┌──────────────────────────── Caddy (TLS) ───────────────────────────┐
             │                    transcribe.dobryakov.net → api:8080                   │
             └────────────────────────────────────┬────────────────────────────────┘
                                                  ▼
  ┌──────────────────────────── api (FastAPI) ───────────────────────────────────┐
  │  /v1/*  REST     /mcp  MCP Streamable HTTP     /u/{token}  страница загрузки │
  │  авторизация по ключу · приём файла потоком на диск · ffprobe-валидация      │
  │  запись задачи в SQLite (status=queued)                                     │
  └───────────────┬───────────────────────────────────────────┬─────────────────┘
                  │ /data (общий volume)                      │
                  ▼                                           ▼
        /data/db.sqlite   /data/work/{job}/   /data/transcripts/{job}.{json,md}
                  ▲
  ┌───────────────┴────────────── worker (1 процесс) ───────────────────────────┐
  │  забирает 1 задачу → этапы в отдельных подпроцессах:                        │
  │  1) ffmpeg → 16k mono WAV, удалить оригинал                                 │
  │  2) диаризация (pyannote | sherpa) → turns.json, выгрузить модель           │
  │  3) ASR faster-whisper → words.json, выгрузить модель                        │
  │  4) склейка слов со спикерами → transcript.json → transcript.md             │
  │  5) удалить WAV, status=done                                                │
  │  лимиты: cpus=3, mem=4g, nice 10                                            │
  └──────────────────────────────────────────────────────────────────────────────┘
```

### Почему этапы идут в отдельных подпроцессах

PyTorch и CTranslate2 не всегда честно отдают память ОС после выгрузки модели. Запуск каждого тяжёлого этапа в `multiprocessing` (spawn) с завершением процесса гарантирует, что на этапе ASR в памяти нет pyannote, и наоборот. Пиковое потребление = max(этап), а не сумма. Плюс падение одного этапа не убивает воркер.

Промежуточные результаты (`turns.json`, `words.json`) пишутся на диск. Если воркер перезапустился посреди задачи, готовые этапы не пересчитываются.

### Порядок этапов

Сначала диаризация, потом ASR. Сама склейка от порядка не зависит, но диаризация обычно быстрее и надёжнее. Если она упала (например, не скачана модель), задача падает рано, не потратив час на ASR.

## 5. Конвейер обработки — детали

### 5.1 Приём и нормализация
1. Файл принимается **потоком на диск** (без чтения в память), лимит размера `MAX_UPLOAD_MB` (дефолт 2048).
2. `ffprobe`: есть аудиодорожка, длительность ≤ `MAX_DURATION_MIN` (дефолт 240). Иначе сразу `400`.
3. Воркер: `ffmpeg -i in -vn -ac 1 -ar 16000 -c:a pcm_s16le work.wav` (2 часа ≈ 230 МБ). **Оригинал удаляется сразу** после успешной конвертации.

### 5.2 ASR
- `language=en|ru|…` → фиксированный язык (быстрее и точнее всего).
- `language=auto` → язык определяется один раз по началу записи.
- `language=multi` → `multilingual=True`: язык определяется на каждом сегменте. **Рекомендуется для смешанных en+ru.**
- Известная проблема Whisper: при фиксированном `en` он может *переводить* русскую речь на английский вместо транскрипции. Поэтому для смешанных записей обязательно `multi`. Это стоит прописать в описании MCP-инструмента, чтобы Claude выбирал правильно.
- Улучшение на будущее: ограничить набор языков (`languages=["en","ru"]`), то есть брать вероятности `detect_language` и выбирать лучший язык только из разрешённых. Это защищает от ложных «украинский/болгарский» на коротких русских фразах.
- Прогресс = `segment.end / duration`.

### 5.3 Диаризация
- Подсказки `num_speakers` / `min_speakers` / `max_speakers` передаются бэкенду. Для `sherpa` без подсказки используется порог кластеризации (`SHERPA_CLUSTER_THRESHOLD`).
- Метки бэкенда нормализуются в `SPEAKER_1..N` **по порядку первого появления** (кто заговорил первым, тот `SPEAKER_1`).

### 5.4 Склейка слов и спикеров
1. Каждому слову ASR назначается спикер с **максимальным пересечением** по времени среди turns диаризации. Если пересечения нет (VAD/диаризация разошлись), берётся ближайший turn.
2. Подряд идущие слова одного спикера собираются в реплику.
3. Реплика дополнительно режется на паузе > `PAUSE_SPLIT_S` (дефолт 2 с) или длине > ~60 с, чтобы тайминги оставались полезными.
4. Наложения речи (overlap) в v1 упрощаются: слово уходит одному спикеру. Отдельно не размечаются.

### 5.5 Результат

Канонический внутренний формат — `transcript.json` (реплики со спикером, start/end, языком и словами). Он нужен для перегенерации Markdown и будущих форматов. Наружу отдаётся **Markdown**:

```markdown
# Собеседование Backend — Иван

- Длительность: 01:47:12 · Языки: en, ru · Модель: large-v3-turbo · Диаризация: pyannote · Спикеров: 2
- Обработано: 2026-10-29 14:02 UTC · job: 01JB7Z…

[00:00:03–00:00:14] **SPEAKER_1:** Hi, thanks for joining. Let's start with a short intro.

[00:00:15–00:01:02] **SPEAKER_2:** Sure. Я последние пять лет работаю в финтехе, mostly on payments…

[00:01:04–00:01:09] **SPEAKER_1:** Great.
```

Тайминги в формате `ЧЧ:ММ:СС`, диапазон на каждую реплику.

## 6. API

Все эндпоинты, кроме `/healthz` и `/u/{token}`, требуют `Authorization: Bearer <API_KEY>`.

### 6.1 REST

| Метод и путь | Назначение |
|---|---|
| `POST /v1/jobs` | Загрузить файл и создать задачу (multipart) → `202 {job_id, status}` |
| `GET /v1/jobs/{id}` | Статус: `queued / processing / done / failed / cancelled`, `stage`, `progress` (0–1), `eta_s`, `position_in_queue`, `duration_s`, `parts_total`, `error` |
| `GET /v1/jobs/{id}/transcript?part=N` | Markdown-транскрипт (весь или N-я часть) |
| `GET /v1/jobs` | Список задач (`?status=&limit=&q=` по названию) |
| `POST /v1/jobs/{id}/cancel` | Отменить queued/processing |
| `DELETE /v1/jobs/{id}` | Удалить задачу и транскрипт |
| `POST /v1/upload-links` | Создать одноразовую ссылку загрузки с параметрами задачи → `{upload_url, job_id, expires_at}` |
| `GET/POST /u/{token}` | Страница загрузки и приём файла по одноразовой ссылке (ключ не нужен, токен = авторизация) |
| `GET /healthz` | Живость + наличие моделей |

Параметры задачи (form-поля `POST /v1/jobs`, тело `POST /v1/upload-links`, аргументы MCP):

| Поле | Тип / значения | Дефолт |
|---|---|---|
| `language` | ISO-код (`en`, `ru`, …), `auto`, `multi` | `en` |
| `model` | `small` / `medium` / `large-v3-turbo` | `large-v3-turbo` |
| `diarization` | `pyannote` / `sherpa` / `none` | `pyannote` |
| `num_speakers` | int | — |
| `min_speakers`, `max_speakers` | int | — |
| `prompt` | строка: имена, термины, компании (подсказка для ASR) | — |
| `title` | строка: заголовок транскрипта | имя файла |

Пример:

```bash
curl -H "Authorization: Bearer $TRANSCRIBATOR_KEY" \
  -F file=@interview.m4a -F language=multi -F num_speakers=2 \
  -F title="Собеседование Backend" \
  https://transcribe.dobryakov.net/v1/jobs
```

### 6.2 MCP-инструменты

| Инструмент | Что делает |
|---|---|
| `create_upload_link(language?, model?, diarization?, num_speakers?, min_speakers?, max_speakers?, prompt?, title?)` | Создаёт задачу в статусе `awaiting_upload` и одноразовую ссылку (TTL 1 ч). Обработка стартует сама после загрузки. Основной путь для Claude.ai (§7) |
| `get_job_status(job_id)` | Статус, этап, прогресс, ETA, место в очереди |
| `wait_for_job(job_id, timeout_s≤50)` | Long-poll: возвращается при смене статуса или по таймауту. Экономит Claude вызовы и токены |
| `get_transcript(job_id, part=1)` | Markdown по частям + `parts_total` |
| `list_jobs(status?, limit?, query?)` | Последние задачи с названием, датой, длительностью |
| `cancel_job(job_id)`, `delete_job(job_id)` | Отмена и удаление |

**Почему транскрипт отдаётся частями.** 2 часа разговора — это ~18–22 тыс. слов, то есть ~30–45 тыс. токенов. Claude Code по умолчанию предупреждает/обрезает ответы MCP-инструментов больше ~25 тыс. токенов (`MAX_MCP_OUTPUT_TOKENS`). Поэтому `get_transcript` режет Markdown на части по ~`PART_TOKENS` (дефолт 15 000) **по границам реплик**, а в начале каждой части повторяет шапку с номером части. Claude читает столько частей, сколько нужно.

Загрузку файла через MCP не делаем: протокол передаёт аргументы в JSON, и гнать 100+ МБ в base64 через контекст модели нельзя. Файл всегда идёт отдельным HTTP-запросом (REST или одноразовая ссылка). MCP оперирует `job_id`.

Описания инструментов (docstrings) пишутся для модели: когда ставить `language=multi`, что `num_speakers` улучшает качество, что обработка занимает десятки минут и надо использовать `wait_for_job`, а не дёргать статус в цикле.

## 7. Как файл попадает на сервер — сценарии

| Клиент | Как загружать | Как Claude работает дальше |
|---|---|---|
| **Claude Code на этом сервере** | Claude сам делает `curl -F file=@/path …` на `http://127.0.0.1:8080/v1/jobs` (файл уже на сервере или скачан) | MCP: `wait_for_job` → `get_transcript` |
| **Claude Code на ноутбуке** | Claude сам делает `curl` на публичный URL с локальным файлом | То же |
| **Claude.ai / Desktop** | См. варианты ниже | То же |

### Варианты для Claude.ai / Desktop

Claude.ai не может отправить на сервер файл, который пользователь приложил к чату. Внутри MCP-вызова доступны только JSON-аргументы.

| Вариант | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **A. Одноразовая ссылка** *(рекомендуется для v1)* | Пользователь: «расшифруй собеседование, 2 человека, en+ru». Claude вызывает `create_upload_link(...)`, даёт ссылку, пользователь открывает её и перетаскивает файл (drag&drop, прогресс-бар). Claude ждёт через `wait_for_job` | Работает из любого клиента и с телефона; ключ не светится в браузере; параметры задаёт Claude | Один ручной шаг (перетащить файл) |
| **B. curl/CLI вручную** | Пользователь сам загружает файл скриптом `transcribe-upload file.m4a --language multi` и даёт Claude `job_id` (или Claude находит задачу через `list_jobs`) | Ноль доп. кода на сервере | Нужен терминал |
| **C. Локальный MCP-мост для Desktop** | Маленький stdio-MCP на ноутбуке (`transcribator-local`) с инструментом `upload_file(local_path, …)`: читает файл с диска и шлёт на сервер | Полностью «на лету» в Claude Desktop, без ручных шагов | Отдельный компонент на ноутбуке; работает только в Desktop, не в вебе |
| **D. По URL** | `transcribe_url(url)`: сервер сам скачивает файл (прямая ссылка, Dropbox, Google Drive с публичным доступом) | Удобно для записей, которые уже в облаке (Zoom/Meet) | SSRF-риски (нужен allowlist/запрет приватных IP), Google Drive отдаёт большие файлы через confirm-страницу |
| **E. Постоянная веб-форма** | Мини-интерфейс под ключом: загрузка, список, просмотр | Удобно без Claude | Больше кода, нужен логин в браузере |

**Рекомендация:** в v1 — **A + B**, и этого достаточно для фактических клиентов (приложение Claude на телефоне → A, Claude Code → сам делает `curl`, по сути B). **C** (мост для Claude Desktop) в бэклоге: ни один из используемых клиентов им не покрывается — в вебе/на телефоне нет доступа к локальному диску, а Claude Code и так грузит файл сам. **D** — когда понадобится транскрибировать записи из облака.

## 8. Авторизация и безопасность

**Ключи.** Пользователь один, но на старте заводим **три ключа** — по клиенту, чтобы отзывать их по отдельности: `claude-code` (Claude Code на этом сервере), `laptop` (Claude Code на ноутбуке), `claudeai` (приложение Claude на телефоне). В `.env` хранятся **SHA-256-хеши** ключей с метками:
```
API_KEYS=claude-code:5e88…,laptop:9f86…,claudeai:2c26…
```
Генерация: `scripts/new_key.py <label>` печатает ключ один раз, а хеш дописывает в `.env`. Сравнение — `hmac.compare_digest`. Метка ключа пишется в лог и в `jobs.created_by`.

**MCP-авторизация по клиентам:**
- *Claude Code (здесь и на ноуте):* заголовок `Authorization: Bearer …`:
  ```bash
  claude mcp add --transport http transcribator https://transcribe.dobryakov.net/mcp \
    --header "Authorization: Bearer $TRANSCRIBATOR_KEY"
  ```
  На этом сервере вместо публичного URL — `http://127.0.0.1:8080/mcp`.
- *Claude.ai / Desktop (remote custom connector):* в интерфейсе коннектора нельзя задать произвольный заголовок. Решение для v1 и возможный апгрейд:
  1. **Секрет в пути URL** (`https://…/mcp/k/<длинный-секрет>`) — **выбрано для v1.** Проще всего: длинный случайный секрет в URL коннектора, сравнение `hmac.compare_digest`. Минус — секрет живёт в URL и может попасть в логи, поэтому `/mcp/k/*` исключается из access-логов, а секрет хранится в БД только хешем.
  2. **Минимальный OAuth-сервер внутри сервиса** (апгрейд на будущее): metadata-эндпоинты, dynamic client registration, страница `/authorize`, где нужно один раз ввести свой API-ключ, затем выдача access/refresh-токенов. Это ~200 строк, и есть готовые хелперы в MCP SDK. Переходим на него, если секрет-в-URL окажется неудобным или появятся другие пользователи.

  ⚠ Перед реализацией этапа 3 сверить актуальные требования Claude.ai к авторизации custom connectors. Они менялись.

**Одноразовые ссылки:** случайный токен ≥ 128 бит, TTL 1 ч, одна загрузка, привязка к заранее созданной задаче. В БД хранится хеш токена.

**Данные:**
- Аудио удаляется: оригинал — сразу после конвертации, WAV — после успешной обработки. При ошибке WAV живёт до 24 ч (для `retry`), потом его удаляет cron-чистка. Задача, по которой файл так и не загрузили, удаляется через 24 ч.
- Транскрипты хранятся бессрочно в `/data/transcripts`, удаляются через `DELETE`.
- Тексты и имена файлов не пишутся в логи (только job_id, длительность, тайминги этапов).
- Права на volume `0700`, бэкап `/data/transcripts` + `db.sqlite` в общий бэкап сервера. Опционально — шифрование диска/volume.
- Обработка полностью локальная, аудио и текст никуда не уходят. HF-токен нужен только при скачивании моделей, в рантайме `HF_HUB_OFFLINE=1`.

**Сеть:** контейнер `api` слушает только docker-сеть Caddy и `127.0.0.1:8080`. `worker` в сеть наружу не ходит. В Caddy настраиваются `request_body max_size 2GB`, увеличенные таймауты на upload и (опционально) rate-limit на `/u/*` и `/v1/*`.

## 9. Ресурсы и производительность

### 9.1 Лимиты

```yaml
worker:
  cpus: "3"          # 1 vCPU всегда остаётся сайтам
  mem_limit: 4g
  memswap_limit: 5g
  environment: [OMP_NUM_THREADS=3, CT2_... cpu_threads=3]
  # внутри: os.nice(10)
api:
  cpus: "0.5"
  mem_limit: 512m
```

Очередь строго FIFO, одна задача за раз (одна строка `processing`, захват через `UPDATE … WHERE status='queued' … RETURNING` в транзакции).

### 9.2 Ожидаемое время на запись 120 минут (3 vCPU, AVX-512, int8)

Это **оценки до бенчмарка**: реальные цифры зависят от доли тишины и `beam_size`. Этап 1 начинается с их замера.

| Этап | Вариант | Оценка |
|---|---|---|
| ffmpeg | — | 1–2 мин |
| Диаризация | `sherpa` | 5–15 мин |
| Диаризация | `pyannote` | 20–60 мин |
| ASR | `small` | 15–30 мин |
| ASR | `medium` | 60–120 мин |
| ASR | `large-v3-turbo` | 50–110 мин |
| **Итого** | `large-v3-turbo` + `pyannote` | **~1.2–3 ч** |
| **Итого** | `small` + `sherpa` | **~25–45 мин** |

ETA в статусе считается по фактической скорости текущего этапа, а для этапов в очереди — по скользящему среднему RTF из прошлых задач (таблица `stats`).

### 9.3 Если нужно быстрее

1. RAM до 16 ГБ и `cpus: 4` — самый дешёвый выигрыш.
2. `beam_size=1` даёт ~1.5–2× на ASR при небольшой потере качества.
3. `sherpa` вместо `pyannote`, если число спикеров известно.
4. Батчинг `BatchedInferencePipeline` в faster-whisper (проверить на CPU, может дать прирост).
5. Крайний вариант — разовая аренда GPU-инстанса для тяжёлых пачек (противоречит «локально», поэтому только как опция).

## 14. Риски

| Риск | Митигация |
|---|---|
| Не хватает RAM, OOM-kill воркера или соседей | Этапы в отдельных подпроцессах, `mem_limit`, бенчмарк до реализации, рекомендация по апгрейду RAM |
| Whisper переводит или путает язык в смешанной речи | `language=multi`, явная подсказка в описании MCP-инструмента, бэклог-пункт про ограничение набора языков. **Подтверждено на реальной записи 2026-10-29:** `multi`/`ru` дают корректный русский, фиксированный `en` действительно переводит русскую речь на английский |
| Галлюцинации на тишине и музыке, зацикливание | VAD, `condition_on_previous_text=False`, отбрасывание сегментов с низким `avg_logprob` / высоким `no_speech_prob` |
| pyannote слишком медленный на CPU | Бэкенд `sherpa`, подсказка `num_speakers` |
| Доступ к моделям pyannote (gated) / смена лицензии | Модели скачиваются один раз и хранятся в volume; есть `sherpa` без регистрации |
| Изменение требований Claude.ai к авторизации connectors | Авторизация изолирована в `auth.py`; Claude Code работает по Bearer независимо от этого |
| Утечка чувствительных записей | Аудио не хранится, ключи и токены хешируются, в логах нет текстов, доступ только по HTTPS |

## 15. Решения (закрытые вопросы)

Зафиксировано 2026-10-29:

1. **Домен** — `transcribe.dobryakov.net`.
2. **Авторизация Claude.ai** — на старте секрет в пути URL (`/mcp/k/<секрет>`), OAuth 2.1 как апгрейд на будущее (§8). Claude Code работает по Bearer независимо.
3. **RAM сервера** — апгрейд до 16 ГБ сейчас не планируется, проектируем под текущие ~3.5 ГБ. Следствие: дефолтную модель (`large-v3-turbo` vs `medium`) подтверждаем замером пиковой RAM на бенчмарке (этап 0); при риске OOM дефолт опускается до `medium`. §9.3 п.1 (апгрейд RAM) неактуален.
4. **Вариант C** (локальный MCP-мост для Claude Desktop) — **в v1 не нужен**, остаётся в бэклоге §13. Используемые клиенты — приложение Claude на телефоне (→ вариант A) и Claude Code на десктопе (→ прямой `curl`); мост не покрывает ни один из них.
